# 系统架构

## 设计目标

系统必须让设备看起来持续在场，同时保持清晰的隐私边界、可恢复性和可观察性。持续监听指麦克风与本地音频前端持续运行，不等同于持续上传、存储或远端推理。

## 分层

### 设备固件

- 音频：ES8311 初始化、I²S DMA、环形缓冲、语音活动检测、唤醒检测、播放队列。
- 交互：GC9A01 界面、LED 状态、BOOT 按键、音量和错误提示。
- 连接：配网、时间同步、TLS、会话重连、协议版本协商。
- 安全：设备身份、最小权限令牌、OTA 校验、回滚、恢复模式。
- 遥测：仅上传明确允许的运行指标，不上传待机原始音频。

### 远端认知服务

- 接收设备事件与会话音频。
- 执行语音识别、对话推理、记忆检索、工具调用和语音合成。
- 将回复音频、字幕、表情和动作提示作为事件返回设备。
- 管理用户确认、敏感操作权限、会话历史与数据保留策略。
- 不假定特定模型供应商；模型和语音服务通过适配器替换。

## 设备状态机

| 状态 | 行为 |
|---|---|
| BOOTING | 硬件自检、分区校验、加载配置 |
| PROVISIONING | 本地配网与设备绑定，不采集远端语音 |
| IDLE_LOCAL | 本地持续采集、VAD/唤醒；不上传原始音频 |
| CONNECTING | 建立加密会话，显示网络状态 |
| LISTENING | 上传当前会话音频，保留短时环形缓冲 |
| THINKING | 等待远端响应，可取消 |
| SPEAKING | 播放回复；第一阶段抑制自回声，后续支持可靠打断 |
| MUTED | 麦克风数据不进入识别或网络链路 |
| ERROR | 给出可恢复错误码，按退避策略重试 |
| RECOVERY | USB/本地恢复和已知良好固件启动 |

任何网络错误都必须回到 IDLE_LOCAL 或 ERROR，不得卡在无提示的伪聆听状态。

## 音频策略

内部基线为 24 kHz、16 位、单声道 PCM。传输层优先使用 20 ms 音频帧与可协商编解码；首版在实测 CPU、内存、延迟和兼容性后选择 PCM 或 Opus。

第一阶段采用可控的轮流对话：设备可持续采集，但在扬声器播放时不把回声误判为用户语音。全双工打断必须在声学回声消除通过实机测试后启用，不能只靠音量阈值假装实现。

## 协议原则

- 传输使用 TLS，并固定协议版本。
- 控制消息采用小型结构化事件；音频使用带序号和时间戳的二进制帧。
- 每次会话拥有独立 ID、超时、取消和关闭事件。
- 服务密钥永不进入固件；设备只持有可撤销的设备凭证。
- 设备必须能够在服务器不可用时独立完成静音、状态提示、恢复和升级回滚。
- 状态和错误码写入文档并保持向后兼容。

## 屏幕语义

屏幕不是装饰，而是系统可信度的一部分。用户无需听声音即可区分待机、正在上传、远端处理、播放、静音、离线和错误。动画不能掩盖真实连接状态。
